## 1. "Triceps rope extensions show no history" — ROOT CAUSE FOUND, not data loss

The app has **two** rope triceps exercises with near-identical names:

| id | name | history |
|---|---|---|
| `…-17-g079` | Cable Triceps Pushdown (Rope) | 7-20, 7-24, 7-27 (all his rope work) |
| `…-16-nm2r` | Cable **Overhead** Triceps Extension (Rope) | **none, ever** |

The **current Full Body Day 3 routine references the Overhead variant**
(`…-16-nm2r`) — but the 7-24 Day 3 session actually performed the Pushdown
(`…-17-g079`). So somewhere between 7-24 and 7-31 the routine's item came to
point at the other exercise. History is keyed by exercise id, so the app
truthfully reports the Overhead as never performed.

**Owner follow-up (same day):** "if I swapped it in the routine then it
doesn't seem like it stored it as the new routine going forward." And later,
the correct theory: "I think maybe we didn't program for this option — swap an
exercise in the routine while working out should prompt to save the edits to
the routine going forward or just this once."

**ROOT CAUSE CONFIRMED IN CODE — the Owner was right; not the sync bug.**
The workout view HAS a mid-workout "Replace exercise" action
(`wo:exreplace` → `wo:replacepick`). Its handler rewrites only the in-flight
workout entry (`en.exerciseId = ex.id; …; saveWorkout()`) and never touches
`state.training.routines`. The Engineer's earlier statements — "no mid-workout
swap feature exists" and the resulting "probable second instance of the sync
defect" reclassification — were both wrong and are withdrawn.

So: the Day 3 routine has always referenced the Overhead variant; the Owner
replaced it mid-workout with the Pushdown each time; sessions recorded the
Pushdown; the routine was never updated because write-back was never
programmed. History lookups key off the routine's exercise id — hence "never
performed."

**Feature (Owner-specified):** on mid-workout Replace, prompt —
"Save to routine going forward" / "Just this once." Additionally worth doing:
disambiguate lookalike exercise names at pick time, and have the workout view's
history lookup fall back to the replaced-in exercise when the routine's
exercise has no history. Scheduled behind the containment release; UI change,
no Architect loop required per the standing scope rule.

## 4. GLP-1 activity pill shows the full shot list — FIXED in `2026-08-01.403-fx`

The day's activity entry should reflect *that day* only (optionally "last shot
X days ago"). The full journal of shots — date, time, units/dose, placement —
belongs in a report/list view, not the pill. He has just taken shot #2 and both
appear on the pill.

**Fix (candidate commit `97f3fac`, pulled forward from Build 2 after the Owner
hit it again 2026-08-01):** `glpCardHTML()` filters doses and symptoms to
`state.selDate`; shot-free days show "last was N days ago". Root cause was
`.slice(0,3)` of the recency-sorted global dose list — day-agnostic by
construction. Comparisons use padded ISO (`toISO`), NOT `glpDayKey`, whose
unpadded `2026-8-1` format never equals a `selDate`. Full journal
(`glpJournalHTML()`) appended under the Weight & dose chart per the Owner's
ruling. C14 covers both (28 assertions).

## 6. Weight oddities — INVESTIGATED, PARTLY LOCATED IN CODE

- **No weight below 183 exists** in the exported record. Lowest weigh-in is
  171.0 (7-29); every sub-183 number in the lift log is machine load
  (105/110/142.5 etc.), not bodyweight. Whatever was seen is either not
  persisted or was a suggestion/display value.
- **The pull-up "strange weight" is real and located.** In
  `buildWorkoutEntries()` (live `index.html`, ~line 6392): when an exercise has
  prior history, set defaults come from `last[k].weight` — the PREVIOUS
  session's logged weight — **even for bodyweight exercises**. The
  `ex.bodyweight ? bw + added` branch only runs when there is no history at
  all. So on 7-29 the pull-up pre-filled/suggested 173.2 (his bodyweight on
  7-22, the previous Day 2) instead of that day's 171.0. `sugW: 173.2` against
  logged `weight: 184` in the 7-29 record shows exactly this. It does NOT use
  startingWeight when history exists — `currentBW()` falls back to
  startingWeight only when no weigh-ins exist at all.
- **Proposed fix (for the sync-rework build, not the frozen candidate):** for
  `ex.bodyweight` entries, always rebase the default to
  `currentBW() + addedWt`, and keep only the *added* weight from history.
