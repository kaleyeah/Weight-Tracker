c11m8-faults — L and Q: a storage-blocked device cannot un-block itself
----------------------------------------------------------------

Bisect:
  9e3f87b (the commit immediately BEFORE the round-30 primitive gate)
      -> OK — 64 passed
  3cd7311 (round-30: "persistence primitives gated at source") and every
      head since, including 87e9d84 and the round-33 head
      -> four assertions fail; the unmodified suite throws and aborts at the
         first one.

Instrumented probe, taken immediately before the failing `saveTraining()`:

  {"proof":false,"onDisk":false,
   "probe":{"blockedBefore":true,"auth":{"ok":false,"why":"blocked"}},
   "raw":null,"released":false,"st":"blocked",
   "after":{"state":"blocked","rev":0},"hardSurvives":true}

M8's design: a failed primary save raises an UNPROVEN (soft) block, and the
athlete's next successful, VERIFIED re-save is what releases it. The round-30
source gate refuses `saveTraining()` whenever `window.m8StorageBlocked` is
true — and that getter is the union that includes the soft block. So the one
action that can clear the block is the action the gate refuses. The device
stays blocked permanently and `wl_training_v1` is never written (`raw:null`).

Failing assertions (all one root cause):
  L: the verified re-save records proof and bytes WITHOUT a reload
  L: only the unproven-save block is released; state reflects the base relationship
  L: synchronization resumes to a real ack
  Q: the verified re-save releases the soft block and journal resolution resumes safely

Operational side effect: with the unmodified suite the first failure throws
inside page.evaluate BEFORE `browser.close()`, so the node process never
exits. That is why stale `c11m8-faults` processes had been left running for
11 hours on this machine; four of them were cleaned up during this round.

NOT FIXED IN ROUND 33, DELIBERATELY. Permitting a durable write while a
storage block is raised contradicts a standing fail-closed ruling ("Corrupt
identity, a raised storage block, an expired deadline ... all refuse
mutation. The gate never 'assumes yes'"). Whether M8's SOFT block is an
exception to that — and how a device is then meant to recover from it — is an
Architect/Owner ruling, not something to slip into a round of test fixes.
