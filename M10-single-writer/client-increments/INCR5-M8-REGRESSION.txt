================================================================
THE TWO FAILURES ROUND 33 REPORTED ARE FIXED — TWO DIFFERENT CAUSES
================================================================

1. c11m8-faults L and Q — the storage-block lockout (PRODUCT fix)
----------------------------------------------------------------

M8's design: a dirty generation whose bytes were never proven to reach disk
raises a SOFT (unproven) block at boot (`m8SoftBlockUnproven`, derived in
`m8Boot`), and the athlete's next successful VERIFIED re-save releases it
(`m8ReleaseUnprovenIfProven`). Round 30 gated `saveTraining()` on
`m10AuthNow()`, which refuses on the whole `window.m8StorageBlocked` union —
and that union includes the soft block. So the one action that could clear the
block was the action the gate refused: the device stayed read-only until
reinstall.

The flags are real and are named exactly as the Architect named them:

    index.html ~8908:  var m8HardBlocked=false, m8UnprovenBlocked=false, ...
    index.html ~8911:  window.m8StorageBlocked  (getter: hard || unproven)
    index.html ~9979:  the getter is EXTENDED by the M10 core block to
                       m8HardBlocked || m8UnprovenBlocked ||
                       m10cHardBlocked || m10cUnprovenBlocked

There is no single combined flag to un-pick and no name to invent: the
soft-vs-hard distinction is `m8UnprovenBlocked` vs `m8HardBlocked`, and the
"combined m8StorageBlocked condition" the ruling protects is the four-way
union above.

Round 34 implements the ruling verbatim: `m8SoftRecoveryAuth()` +
`m8SoftBlockRecoverySave()` in M10-BLOCK-5 (search `Z1 (round-34 rulings 1 and
2)`), reached ONLY from the `saveTraining` arm of the source-gate wrapper and
only when `m10AuthNow().why === "blocked"`.

Result: c11m8-faults runs to completion and exits 0 for the first time since
round 30. See INCR5-MATRIX/raw/c11m8-faults.txt.

2. c11m8-quota B6/13 — a DIFFERENT cause (HARNESS fix, disclosed)
-----------------------------------------------------------------

Round 33 filed this under the same root cause. It is not. Probing the failing
run rather than assuming:

    ballast ~4992KB; preNet state=clean blocked=false
    primaryPersisted=false commitReqs=0; dirty bytes: null

`dirty bytes: null` means `saveTraining()` never ran at all — not that it ran
and was refused by a block. That harness mocks NO lease route, so under the
wired gate the signed-in device is not the writer and every mutating save is
refused as "not-holder" long before M8's storage handling is reached. The
suite had stopped testing what it is named for.

Fixed with the SAME disclosed harness change already accepted for
`c14-correctness-fixes` and `c11m8-faults` in round 33: answer
`**/api/cf/writer/lease` as a granting server. Harness only — no product
change, and not one assertion was weakened, removed or reworded.

Result: 6 passed, exit 0, with a real verified dirty marker
(`{"gen":2,"persistedGen":2,...}`) before any network action.

================================================================
OPERATIONAL NOTE
================================================================

Before round 34, a failing `c11m8-faults` threw inside page.evaluate BEFORE
`browser.close()`, so the node process never exited and stale runs
accumulated for hours. The matrix runner now wraps every suite in
`timeout -k 20 <N>`, so a hanging suite is killed and reported as TIMEOUT
rather than left behind.
